# project-governance（项目治理）

## 这是什么

对仓库治理做**审计 / 建立 / 最小修复**。只在指令、文档、测试、所有权、交接或工作流已经产生**可证明的**协调成本、漂移或相互冲突的 Authority 时使用。

一句话判据：治理只在它能降低协调、传播或高代价失败的生命周期成本时才成立。

## 不做什么

- 不搭项目骨架（见 **project-bootstrap**）；
- 不做产品架构评审、日常编码或通用清理；
- 不改产品代码，只动范围内的治理产物与治理检查项；
- 不强加固定文件名、角色、计划、所有权表、套件数量或流程仪式。

## 三种模式

| 模式 | 行为 |
|---|---|
| **Audit**（审计） | 只读。报告证据与最小修正，不做任何改动 |
| **Establish**（建立） | 建立治理产物，但只建通过生命周期测试的 |
| **Repair**（修复） | 按固定顺序做最小修复，优先删减而非新增 |

## Authority 与生命周期测试

每个耐久事实只保留**一个**可独立编辑的 Authority，且尽量靠近它所约束的行为。优先级：

1. 代码、类型、schema、配置或约束；
2. 针对该 Authority 的机械校验；
3. 可靠推导；
4. 只有当重新发现或误用的代价高于维护代价时，才用持久化文档。

新增任何规则、文档、角色、交接、状态文件或检查之前，必须先回答：它防止的已证实的反复/高代价失败是什么？更靠近的可执行 Authority 为何不够？谁在什么事件下读它或跑它？谁维护它、何时退役？预期节省是否超过传播与维护成本？**答不上来就不加。**

## 审计看什么

竞争 Authority、重复事实、手工同步；过时的指引、已完成的工作、被当成当前事实的临时状态；挡不住已证实冲突的所有权与交接；没有真实读者或执行链路的文档与检查；只锁措辞和实现形状、不保护任何可观测约束的 flaky 检查；以及只为管治理而存在的治理。

## 最小修复顺序

1. 删除过时、重复或可可靠推导的表述；
2. 选定最近的 Authority，把副本换成推导、校验或链接；
3. 去掉不必要的传播、所有权状态与交接；
4. 只有当减少的传播/回退成本超过其生命周期成本时才加边界；
5. 只有通过生命周期测试时才加持久化说明或检查。

## 输出

根因、当前或建议的 Authority、**keep / change / remove** 判定、最小有序修正、验证方式、剩余实质风险。除非用户要求，不生成报告文件。如果现有治理比它要防止的失败更便宜，就建议不做任何改动。

## 配套

- **project-bootstrap**：搭最小可运行技术底座，与本 skill 正交。
- **advisor-review**：需要第二模型只读评审时可叠加使用。
