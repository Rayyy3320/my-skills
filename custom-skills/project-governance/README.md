# project-governance（项目治理）

## 这是什么

一个多 agent 协作的"建政工具"：为软件项目搭建一套文档化的治理结构。项目启动、收编存量仓库或怀疑结构漂移时运行**一次**，产出常驻治理文档后即退出——之后项目自带规则，任何会话只依赖项目自身文档，不再需要本 skill。

## 解决什么问题

多个 AI agent（或人与 agent 混合）协作时的常见混乱：谁都能改任何文件、耐久知识散落在对话记忆里、文档越堆越多、测试套件无限膨胀。本 skill 把这些约束固化成一套文档骨架。

## 三种模式

| 模式 | 场景 |
|---|---|
| **bootstrap**（绿地） | 给无结构的新项目搭完整骨架 |
| **audit**（体检） | 对比现状与理想骨架，报告并补齐缺口，幂等可重入 |
| **adopt**（收编） | 把无结构的存量仓库最小移动迁入骨架 |

执行流：检测 → 给出计划 → 用户确认 → 应用 → 输出治理地图。

## 核心原则

1. **目录树 = 所有权表**：每个目录有唯一归属，表里一行、盘上一棵，冲突开工前可见。
2. **共享记忆只有两处**：用户和仓库文档。耐久知识必须落文档，不依赖任何 agent 的记忆。
3. **文档分两层**：常读层（规则 + 维护协议，严格行数预算，增删靠替换）与按需层（需求基线、契约、任务清单）。
4. **维护规则内嵌**：以"条件触发一行规则"写进常读文档，agent 每次开工反正要读，顺手就完成了维护。
5. **测试只减不增**：每套件一个职责，验收测试随波退役，只锁不变量、不锁文案措辞。

## 典型产出

常读文档（≤80 行）、所有权表、各域 `TASKS.md`、`contracts/`（跨域契约）、当前波次需求基线、收敛后的 `tests/`，最后一页"治理地图"（文档 → owner → 谁在什么时候读）供用户一眼验收。

## 配套

需要第二模型只读评审、疑难升级或设计预审时，可搭配 **advisor-review** skill 使用（两者正交、单独开关，仓库不留痕迹）。
